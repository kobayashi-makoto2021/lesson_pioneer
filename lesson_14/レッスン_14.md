### プレイテストってなに？

作った人以外に遊んでもらって、感想をもらうことを **プレイテスト** というよ。

作った人には、実は**見えていないもの**がたくさんあるんだ。

- 何をすればいいか、遊ぶ人にはわからない
- ボタンがどこにあるか気づかれない
- 自分は知っているから気にならないけど、初めての人にはむずかしい
- 作った人が試さない操作をされて、バグが見つかる

だから、ゲーム会社では必ずプレイテストをするんだよ。今日はそれを本物と同じようにやってみよう。

### 感想の伝え方 — 「よかった」＋「気づいたこと」

友だちの作品を遊んだら、この2つをセットで伝えよう。

| 伝えること | 例 |
|---|---|
| **よかったところ**（必ず1つ以上） | 「toioが逃げる動きが面白かった」 |
| **気づいたこと** | 「最初、何をすればいいかわからなかった」 |

> **大事なルール：** 「つまらない」「へた」はナシ。**作品を良くするための言葉**だけを伝えよう。「気づいたこと」は、悪口じゃなくてプレゼントだよ。

### もらった感想は、全部直さなくていい

感想をたくさんもらうと、全部直したくなる。でも、時間は限られているよね。

こうやって選ぼう。

| 優先 | どんなもの？ |
|---|---|
| **1番** | **バグ**（動かない・エラーになる・止まらない） |
| **2番** | **わからない**（遊び方が伝わらない・説明がない） |
| 3番 | もっと面白くなる工夫 |
| やらない | 直すのに時間がかかりすぎるもの |

**バグと「わからない」を先に直す。** これだけで作品はぐっと良くなるよ。

### 「説明」は最強の改善

「遊び方がわからない」と言われたときは、プログラムを作りかえなくても直せることが多いんだ。

- 最初に「〇〇と言う」で遊び方を表示する
- 背景に文字で書いておく
- スプライトに説明を言わせる

**5分でできて、効果は大きい。** 迷ったらまずこれをやろう。

## ミッション

友だちに遊んでもらって、作品を仕上げよう！

---

### ステップ1: プレイテストの準備

遊んでもらう前に、確かめておこう。

- [ ] 旗を押したら、最初から始まる？（前の状態が残っていない？）
- [ ] 一通り最後まで動く？
- [ ] 遊び方を、口で説明できる？

そして、感想を書いてもらう紙を用意しよう。

```
作品名：                     作った人：

よかったところ：

気づいたこと：
```

---

### ステップ2: 遊んでもらおう

友だち2〜3人に遊んでもらおう。ルールはこれだよ。

**作った人のルール**

- **口出ししない！** 遊んでいる人が迷っても、すぐには教えない
- どこで止まったか、どこで迷ったかを**よく見てメモする**
- 「そこはそうじゃなくて…」と言いたくなったら、それが**直すべきところ**だよ

**遊ぶ人のルール**

- まず自分で考えて操作してみる
- よかったところを**必ず1つ**伝える
- 気づいたことは、作品を良くする言葉で伝える

```
メモ：どこで迷った？ どこで止まった？



```

---

### ステップ3: 直すことを決めよう

もらった感想を、優先順に並べよう。

| 優先 | 直すこと | やる？ |
|---|---|---|
| 1（バグ） | | ☐ |
| 2（わからない） | | ☐ |
| 3（もっと面白く） | | ☐ |

> **時間を計算しよう：** 今日残っている制作時間は30分くらい。全部はできないよね。**上から順に、できるところまで**やろう。

---

### ステップ4: 仕上げよう

決めたことを、上から順に直していこう。

**仕上げのチェックリスト**

- [ ] バグは直った？
- [ ] 遊び方の**説明**を入れた？
- [ ] 旗を押したら、ちゃんと最初から始まる？
- [ ] 選んだ**3つの概念**は作品に入っている？
- [ ] 作品に**タイトル**をつけた？

> **やってはいけないこと：** 今日、新しい大きな機能を作りはじめること。次回は発表だから、**動かなくなるリスクは取らない**でね。

---

### ステップ5: 発表の準備

次回はいよいよ発表だよ。話すことを決めておこう。**1人3分**だよ。

```
① 作品のタイトル：

② どんな作品？（ひとことで）：

③ 使った概念3つと、どこで使ったか：
   ・
   ・
   ・

④ いちばんがんばったところ・くふうしたところ：

⑤ むずかしかったこと、どうやって解決した？：

⑥ もっと時間があったらやりたいこと：
```

**発表のコツ**

- 実際に動かしながら話そう。見せるのがいちばん伝わるよ
- うまくいかなかったところも話していい。**そのほうが面白い発表**になるんだ
- 原稿を全部読まなくていい。上のメモを見ながら話せば大丈夫

## まとめ

- 作った人には見えないものがある。だから**プレイテスト**をする
- 感想は「**よかったところ**」＋「**気づいたこと**」のセットで伝える
- もらった感想は全部直さない。**バグ → わからない → 面白く** の順で選ぶ
- 「遊び方の**説明**を入れる」は、短時間で効果が大きい改善
- 発表前日に大きな機能を作りはじめない。**動く状態を守る**
- 次回は発表！ うまくいかなかった話も、りっぱな発表の材料だよ
